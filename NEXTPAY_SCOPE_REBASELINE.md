# NextPay Scope Rebaseline

## 1. Project Rebaseline

### Current Build Status

The NextPay site has moved beyond a basic landing page and now includes a substantial production-ready framework:

- homepage with primary funnel flow
- services index and service detail pages
- industries index, industry detail pages, sector pages, and sub-sector pages
- pricing / custom quote flow
- statement upload flow
- contact and lead capture flows
- trust logo sections
- merchant savings and case study style sections
- admin review and quote workflow structure
- persistent route architecture, metadata, and supporting content models

### What Is Complete

The following should be considered structurally complete unless the client requests a true redesign:

- site architecture and routing
- navigation framework
- service taxonomy
- industry taxonomy
- CTA framework
- quote/contact intake framework
- statement upload workflow framework
- admin workflow foundation
- reusable section/component system

### What Is Placeholder or Directional

The following areas are currently best understood as directional unless the client has explicitly approved the final content:

- detailed service-page copy
- industry-specific microcopy
- vendor / hardware selections
- trust logos and partner logo treatments
- merchant savings examples
- calculator / pricing assumptions
- case studies and testimonials
- generated or substituted imagery

### Scope Clarification

The build should be treated as:

- a custom website framework with conversion flows
- a white-labeled content structure
- a flexible foundation for final business-specific inputs

It should not be treated as:

- a fully finalized product catalog
- a verified hardware inventory
- a compliance-approved pricing engine
- a fully asset-complete brand site
- a claim-complete sales site without client review

### Recommended Working Rule

From this point forward, all requests should be classified into one of two buckets:

1. framework / UX / structural changes
2. content / asset / claim completion that requires client inputs or approvals

That distinction is necessary to prevent open-ended scope expansion based on assumptions.

## 2. Client Dependency Buckets

### Client-Provided Inputs Required

The following items should come from the client before they are treated as final-production content:

- approved logo files
- approved vendor / partner brand assets
- approved hardware / POS platform list
- approved service claims
- approved pricing assumptions
- approved financing language
- approved testimonials
- approved case studies
- approved merchant savings examples
- approved industry-specific positioning
- approved brand color guidance / hex values if stricter branding is desired
- approved hero / service / industry imagery, or explicit approval to use generated imagery

### Client Decisions Required

The following are business decisions, not implementation-only tasks:

- which product lines should be featured
- which vendors should be publicly named
- whether specific hardware should have dedicated pages
- whether pricing examples should be published
- whether dual pricing / cash discount language is acceptable as written
- which industries deserve detailed landing pages first
- which proof points can be presented publicly

### Revvit / Build-Team Responsibilities

The build team can responsibly handle:

- page layout and UX improvements
- navigation refinement
- responsive behavior
- funnel structure
- reusable content models
- placeholder-to-final content integration
- technical integrations
- file upload / lead routing / admin workflow implementation
- controlled replacement of approved assets and copy

### Stop-and-Wait Triggers

Work should pause for client input when a request depends on:

- exact brand/vendor logos
- exact hardware/product mappings
- exact pricing numbers
- exact underwriting or financing claims
- exact customer proof points
- exact industry-specific operational claims
- final approved imagery

### Practical Interpretation

If the client asks for highly specific content without supplying the source material, the site should not keep expanding through assumption alone.

Instead:

1. preserve the existing framework
2. mark the section as pending client content
3. request the missing source inputs or written approval for generated substitutes

This keeps the project aligned with the original working model: build the structure first, then finalize the details with client review and supplied materials.
